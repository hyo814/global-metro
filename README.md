# 어디로

전 세계 대중교통을 **한국어로** 찾는다. 63개국 368만 개 정류장.

현지 표기를 몰라도 된다. `신주쿠`라고 치면 `新宿`을 찾아주고, 결과는 한국어와
현지 표기를 나란히 보여준다. 역에서 표지판과 그대로 맞춰볼 수 있게.

```
신주쿠  →  긴자 4초메                          28분 · 환승 1회
新宿   →  銀座四丁目

  15:00  [4]  新宿 → 大門            15:16   7정거장
    도보 2분
  15:22  [1]  大門 → 東銀座           15:26   2정거장
    도보 2분  → 銀座四丁目
```

## 왜 만들었나

해외에서 대중교통 정보가 그 나라 말로만 되어 있어 뭐가 뭔지 알 수 없었다.
번역기는 정류장 이름을 엉뚱하게 옮기고, 지도 앱은 현지 표기를 알아야 검색이 된다.

그래서 **한국어로 검색하면 현지 표기로 바꿔 찾고, 결과는 둘을 나란히** 보여주는
것을 만들었다.

## 시작하기

```bash
# 1. 자격 증명
cp .env.example .env          # MOBILITY_REFRESH_TOKEN, ANTHROPIC_API_KEY

# 2. GTFS 내려받기 (약 15.6GB, 1~2시간. 중단해도 이어받는다)
python3 backend/fetch_gtfs.py

# 3. 검색 인덱스 만들기 (약 10분)
python3 backend/build_index.py

# 4. 실행 — 같은 와이파이의 폰에서도 열린다
./dev.sh
```

`fetch_gtfs.py`는 `--country JP`처럼 일부만 받을 수도 있다. 전 세계가 필요 없으면
그게 빠르다.

## 구조

```
backend/
  fetch_gtfs.py    Mobility Database에서 GTFS zip 일괄 수집
  build_index.py   전 세계 정류장을 SQLite FTS5 하나로. 검색 1ms
  gtfs.py          피드 하나의 시간표 조회 (출발 안내판)
  router.py        RAPTOR 경로 탐색 (A에서 B까지)
  translate.py     한국어 <-> 현지 표기 변환, 영구 캐싱
  app.py           Flask API
frontend/          React + Vite
```

**무거운 것을 전역으로 모으지 않는다.** `stop_times`는 431M행 28GB다. 정류장 하나는
피드 하나에만 속하므로, 검색으로 정류장을 찾은 뒤 그 피드의 zip만 열면 된다.
전역 인덱스에는 정류장만 담아 368만행 533MB이고 검색이 1ms 안에 끝난다.

**경로 탐색은 패턴 단위로 돈다.** 헬싱키는 trip이 385,428개지만 정차 순서로 묶으면
패턴이 1,167개라 스캔 대상이 300배 줄어든다. 시각표 펼치기 1.5초, 탐색 6~9ms.

**피드 경계를 넘는다.** 도쿄에서 버스와 지하철은 다른 피드에 있다. 구역에 걸친
피드를 좌표로 이어 하나의 망으로 본다. 신주쿠에서 시부야까지 피드 12개를 묶어
26분에 나온다.

**걸어도 되는 거리를 고른다.** 환승을 줄이려면 더 걸어야 할 때가 있다. 신주쿠에서
350m 한도면 지하철 한 정거장 + 환승 1회, 500m면 10분 걸어 환승 0회 — 둘 다 26분이다.

## GTFS를 다루며 만난 것들

규격만 읽고는 알 수 없고, 실제 피드를 세어봐야 나오는 것들이다. 괄호 안은 받아둔
피드에서 해당되는 비율이다.

| | 내용 |
|---|---|
| **24시를 넘는 시각** | `25:30:00`은 다음날 01:30이다. `HH:MM:SS`로 파싱하면 깨진다 (31%) |
| **`calendar.txt` 없음** | 요일 반복 없이 `calendar_dates.txt`만 있는 피드 (37%) |
| **`frequencies.txt`** | `stop_times`가 시각표가 아니라 배차 패턴이다. 한 정류장에서 2행이 85건으로 펼쳐진다 (16%) |
| **역과 승강장** | `location_type=1`인 역은 `stop_times`가 0행이다. 정차는 자식 승강장에 있다 |
| **빈 행선지** | `trip_headsign`이 공백뿐인 피드 (13%). 종점 이름으로 채운다 |
| **고정폭 패딩** | `route_id`에 공백이 붙어 조인이 137,715건 중 95건만 맞았다 |
| **이름 중복** | 같은 이름 정류장이 인덱스의 48%. 500m 안이면 한 곳으로 묶는다 |
| **국가 표기 오류** | 국경을 걸치는 피드의 `locations` 첫 항목이 이웃 나라다. 355,497개짜리 독일 피드가 프랑스였다 |
| **다국어 한 칸** | `태국어;영어`를 통째로 번역하면 같은 말이 두 번 나온다 |

## 데이터

| 출처 | 범위 | 비고 |
|---|---|---|
| [Mobility Database](https://mobilitydatabase.org/) | 63개국 2,721개 피드 | 무료, 리프레시 토큰 필요 |
| [ODPT](https://developer.odpt.org/) | 도쿄메트로 등 | `fetch_odpt.py` · 가입 후 관리자 승인 |
| [TAGO](https://www.data.go.kr/) | 한국 버스 | `fetch_korea.py` · GTFS가 아니라 변환 필요 |

**한국은 Mobility Database에 없다.** 데이터가 없는 게 아니라 GTFS가 아닐 뿐이다.
TAGO가 공공데이터포털로 전국 버스 정보를 여는데 시각표가 아니라 배차간격을 준다.
`fetch_korea.py`가 이를 `frequencies.txt`로 변환한다. 정류장 간 소요시간은 주지 않아
좌표 거리로 추정하며, 그 사실을 `feed_info.txt`에 적어 둔다.

**일본 철도는 대부분 공개되지 않는다.** JR은 어느 경로로도 GTFS를 내지 않는다.
도쿄 기준으로는 버스 전체 + 도에이 지하철(이미 포함) + 도쿄메트로(ODPT 승인 후)가
현실적인 최대치다.

## 검증

핵심 모듈은 각자 실제 피드로 자기를 검사한다.

```bash
python3 backend/gtfs.py        # GTFS 함정 5개를 피드 4개로
python3 backend/router.py      # 경로 86개·승차 232구간의 시간 정합성
python3 backend/translate.py   # 번역 캐시와 질의 변환
```

`router.py`의 검사 하나는 **출발 안내판과 경로 탐색을 서로 대조**한다. 같은 일을
SQL과 파이썬으로 따로 구현했으므로, 두 결과가 어긋나면 둘 중 하나가 틀린 것이다.

## 알려진 한계

- 경로 탐색은 한 구역 안에서만 된다. 도시를 건너뛰는 장거리는 대상이 아니다.
- 도보 구간은 직선 거리로 계산한다. 실제 보행로가 아니다.
- 번역은 처음 보는 이름에서 5~8초 걸린다. 한 번 번역하면 영구 캐싱된다.
- 베트남·한국 등 일부 국가는 피드가 없어 검색되지 않는다.
